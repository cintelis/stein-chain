Why post-quantum, and why now

A cryptographically relevant quantum computer would break ECDSA and Ed25519, the signatures that secure most of today's blockchains. Funds held under those keys could be spent by whoever breaks them, and a chain cannot change its signature scheme overnight.

Stein Chain starts post-quantum from genesis instead of retrofitting it later. Keys and signatures carry a scheme tag, so new algorithms, including the final FIPS 206 when it is published, can be added without changing the transaction format.

  • FIPS 204 ML-DSA-44 and ML-DSA-65 signatures, through AWS-LC
  • Draft FIPS 206 FN-DSA-512 (Falcon) for account keys, the default for new accounts
  • BLAKE3 hashing, with a separate domain context for every use
  • Borsh encoding for everything that is hashed or signed

How it works

Security first, then throughput: nothing a block proposer claims is taken on trust.

Every validator verifies everything

Blocks carry their signatures as witnesses. Each validator checks every signature and the state root itself before it votes, and rejects a block that arrives without them. Signatures are pruned only after finality.

Small post-quantum transfers

An FN-DSA-512 transfer is 789 bytes, against 2,543 bytes with ML-DSA-44. Public keys are registered on chain once, so later transfers carry only the signature.

Verified once per node

A signature is verified when it enters the mempool and cached, so block import does not repeat the work. The cache is keyed so it can never vouch for different bytes.

Built to fail safe

Consensus code uses checked arithmetic and never panics, unsafe Rust is forbidden, and supply conservation is tested. Bounded mempool and caches keep a node's memory in check.

Scales by role, not by machine size

A validator core stays small. RPC nodes, signature-verification workers and the archive scale out separately, so validators can run on modest hardware.

Shard-ready

Sharding is not part of version 1, but every protocol change must keep the invariants that allow it later, and the scaling path runs through signature aggregation and validity proofs.

Roadmap

Stein Chain runs today as a single-validator devnet. Peer-to-peer networking and BFT consensus come next.

  1. Done
    Devnet

    Post-quantum crypto, transactions, state, fsynced block log, RPC and CLI wallet.

  2. Done
    Followers and PQ TLS

    Follower nodes that re-verify every block, over TLS 1.3 with X25519MLKEM768 key exchange.

  3. Done
    FN-DSA-512 accounts

    789-byte transfers, ahead of the final FIPS 206.

  4. Done
    steinscan and steinwallet

    A live block explorer, and a browser wallet that signs with FN-DSA.

  5. Next
    Hardening

    Fuzzing of every decoder, property tests, state on disk, RPC rate limits, archive offload.

  6. Planned
    Peer-to-peer

    QUIC with post-quantum TLS, transaction gossip, compact block propagation.

  7. Planned
    Consensus

    BFT proof of stake with ML-DSA votes, a formal model checked for safety, and deterministic simulation testing.

  8. Planned
    Public testnet, then mainnet

    Faucet and indexer, two independent audits, a bug bounty and multi-region load tests before genesis.

  9. Designed
    WebAssembly smart contracts

    Metered execution, asynchronous receipts and token standards. Design written, not built.

FAQ

Can I buy STEIN?

No. Stein Chain is a devnet. STEIN on it has no value, and there is no token sale. Total supply, allocation and issuance have not been decided.

Can I use MetaMask?

No. MetaMask signs with ECDSA, which Stein Chain does not accept by design. Use steinwallet: it creates an FN-DSA-512 account, and your key never leaves your browser.

Why adopt FN-DSA before FIPS 206 is final?

FN-DSA-512 makes transfers about 69% smaller than ML-DSA-44. Stein uses the current draft for account keys only, pinned to one implementation; validators stay on ML-DSA. When the final standard is published it gets a new scheme tag, and the draft stays valid so the chain can replay its own history.

Is it safe to hold real value on Stein Chain?

Not yet. The devnet has one validator and can be reset at any time. Consensus, audits and a public testnet come before any mainnet.

Is the code open?

Yes. The node, specification and tooling are on GitHub.
